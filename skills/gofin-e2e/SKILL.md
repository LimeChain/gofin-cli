# GoFin E2E verification

Verify the intended live-write workflow end to end before human verification. Exercise the current build through the public CLI, broker, real adapters, financial execution and durable settlement, and establish that the scenario produces the expected financial effects. Reads support preparation and verification; read-only checks, startup, previews, transaction hashes and component tests cannot substitute for a successful live-write scenario. Financial baseline restoration is optional and does not determine whether the scenario passes.

## Invocation and authority

The user's invocation of this skill, or request for GoFin live E2E verification, authorizes **automatic development approval** for the selected test: setup with supplied disposable credentials, agent-selected test parameters when omitted, financial writes, bounded retries, recovery, and optional restoration. Explain the concrete scenario before the first write, then proceed without asking for approval again. The same authorization covers fixes, rebuilding, and retesting within that scope. Authoring/reviewing this skill or discovering it during ordinary coding is not an instruction to move funds. Honor narrower user constraints.

Use the separate `gofin-dev` / `gofin-dev-broker` examples through `make dev-env-*` with `DEV_MODE=live`. Real adapters, financial policy, durable records and settlement checks remain active; the development authorizer approves automatically. Never bypass GoFin execution, weaken checks, edit journals to manufacture success, or introduce an approval-disable switch into shipped binaries. Protected installation and real Touch ID remain separate human verification cases.

Use defaults of **$20 maximum per movement and $200 total test allocation**, including execution, retries and any optional restoration costs. For complex actions that need more, the agent may override either default without another permission request: record the concrete need, fresh valuation, revised finite limits and available disposable funding before the affected write, then report the adjustment. Use the smallest sufficient increase; do not treat an override as unlimited spending. Explicit limits supplied for the current task still govern unless the human allows their override. Retries, rebuilds and new environments do not reset spent costs or allocation accounting. Align the isolated development environment's financial policy and operation/plan authorizations with the selected scenario as part of setup. The agent may configure those development-only limits and obtain or revise automatically approved authority without human intervention, including after a justified budget override. Account for the different units: the test allocation measures capital and costs, while GoFin's rolling budget counts gross movement across commands, including existing usage and unresolved reservations. Keep both finite and sufficient for the scenario; do not reset history to obtain headroom. See [policy alignment](references/environment.md#align-development-policy-with-the-scenario). Keep production settings untouched and retain valuation, permission, fee/slippage, authorization and duplicate checks.

## 1. Prepare the matching environment

Work in the GoFin checkout containing the change. Read its `AGENTS.md`, relevant implementation/testing guidance and diff. If installed from another worktree, prefer this checkout's `skills/gofin-e2e/` and its repository-relative references. Follow [environment setup](references/environment.md) for inventory, import and lifecycle commands. Reuse this worktree's applicable imported live environment: `dev-wallet` for EVM and `dev-solana-wallet` for Solana. Do not ask the human to choose the protected wallet.

Never read installed production secrets. Development credentials are supplied in the repository's gitignored `.env` file, or an explicitly supplied path to it. This disposable file is agent-accessible data: import without printing or shell-sourcing it. `ETH_WALLET_PK` is an accepted alias for `GOFIN_DEV_EVM_PRIVATE_KEY`; it imports the EVM development wallet as `dev-wallet`. The supplied Solana dev signer uses `SOLANA_PRIVATE_KEY` (alias of `GOFIN_DEV_SOLANA_PRIVATE_KEY`) and imports as `dev-solana-wallet`; its presence does not prove current balances or an existing import. For Solana-only work, use `DEV_ENV=solana` and `DEV_IMPORT_FLAGS='--provider solana'` to avoid importing unrelated credentials. The importer reads only supported credential keys and ignores unrelated assignments in combined exports. Prefer its provider filter where available. For a mixed scenario where another supported provider's incomplete credentials cannot be filtered, use a private mode-0600 temporary dotenv file containing only the required assignments; never overwrite the human's file, print values, or shell-source it. Imports survive rebuilds; a missing dotenv file does not mean credentials are missing. Worktree isolation does not isolate live accounts. Respect known concurrent tests and shared budget; unexpected balance/nonce activity requires reconciliation, not killing another broker or taking its funds.

For Solana/Jupiter, follow the [Solana environment notes](references/environment.md#solana-and-jupiter). Use `network: "solana"`, `cluster: "mainnet-beta"`, and exact case-sensitive mints. Verify both SPL Token and Token-2022 account/extension support for the actual operation. Jupiter is keyless by default. Finalized transaction inclusion plus verified financial effects establishes settlement; order placement, confirmed inclusion and keeper request acceptance do not. For CEX transfers, inspect the exact asset/network deposit and withdrawal routes, approved destination and receiving-side evidence; exchange support alone does not establish that GoFin composes that route.

Build/start the matching pair and inspect `connections`, `capabilities`, `operations`, and `policy show` through its public CLI with `--json`. Record worktree, commit plus dirty diff identity, environment and build ID. Reconcile existing in-scope pending operations before replacement; do not adopt or wipe unrelated pending work to obtain a clean test.

## 2. Define the scenario and pass conditions

Use the human's scenario. If none is supplied, derive the smallest meaningful live-write scenario from the new behavior, disposable accounts and current discovery. Choose exact networks/assets, quantities, verified owned destinations, finite fee/slippage bounds and the intended authorization mode. Amounts must fit verified venue minimums comfortably below the budget. Resolve these choices yourself when evidence is unambiguous; ask only for unavailable prerequisites or choices that expand the user's scope.

A swap change needs quote/permission/swap and verified input/output settlement; a transfer needs verified source debit and destination credit; a named-plan change needs the actual ordered plan, dependent funding and completion. Standalone writes cannot substitute for named-plan execution. Reverse transactions are optional unless they are themselves behavior the human asked to verify. Do not drop an explicitly requested repayment, withdrawal or return leg by relabeling it optional restoration. Never substitute an easier network, venue or account mode, or read-only evidence, and claim the original scenario passed.

Write a private record in ignored `.context/test-runs/<scenario>/` using the [report template](../../docs/testing/report-template.md). Record:

- Intended behavior, assertions, authorization mode and finite test scope.
- Initial allocations, tracked balances, collateral/debt, positions, open orders and relevant permissions/allowances.
- Fresh USD valuation, allocation at each stage, movement debit plus fee bounds, spent costs and remaining budget. Count collateral and borrowed proceeds separately; don't double-count receipt tokens or net debt off assets.
- Intended final holdings, positions/debt and permissions, plus any optional restoration chosen. If restoring, check return-route permissions, minimums, liquidity and gas and include its costs. An unavailable or impractical return path is not a prerequisite blocker for the live-write scenario. Bound allowances; do not grant unlimited approvals or alter unrelated existing unlimited allowances to run a test.
- Expected financial effects, gas, fees, interest and any retained exposure, and the independent evidence that will establish each assertion.

Present the concrete scenario, expected final state and budget as a progress update, not another permission gate. If a complex scenario needs larger limits, apply the documented override above. If funding or another concrete prerequisite is still unavailable, continue independent engineering and report what is missing. Difficulty restoring the baseline alone must not block execution or a pass.

## 3. Rehearse, build and execute

Run focused regressions. Before live writes, rehearse the same sequence and authorization mode through CLI → broker → engine → real adapter preparation → isolated transport → durable settlement, following the [workflow rehearsal contract](../../docs/testing/README.md#complete-workflow-rehearsal). Add/repair missing fixtures; generic `synthetic.uncertain-write` proves environment recovery only. Use owned forks where contract behavior needs verification. Inject destructive failures in isolated tests, not funded live accounts. Cover materially different states and relevant partial, zero-fee, expiry and recovery cases.

After source edits, stop/start the selected live environment to rebuild both binaries while preserving credentials and financial history. Discover commands with `--help`, `capabilities`, `explain`, `schema`, previews and results. Use `make dev-env-cli DEV_ENV=<selected> ARGS='... --json'` for every financial action; never fall back to `make dev` or bare installed `gofin`. Quote generated inputs safely; never evaluate JSON as shell code or put secrets in arguments.

For each step:

1. Refresh state/quotes and preview the concrete operation. Recheck allocation, gross debit, costs, any chosen restoration reserve and remaining GoFin policy. If test limits need adjustment, document the finite override before writing; refresh GoFin authority through its normal commands when required. Never silently enlarge an issued authorization.
2. Request the intended exact, boundary or named-plan authority using GoFin's normal commands. Automatic development approval still requires those commands. Record review hashes, grant/plan/step IDs and immutable attempt identities.
3. Submit explicitly once. Preserve logical request, operation, venue and chain identities. Poll `status OPERATION_ID --json` and relevant protocol/plan status with bounded waits for verified terminal evidence. A timeout, hash or accepted HTTP response is neither a verified failure nor a pass.
4. Verify expected balances, effects, costs and permissions with public reads. Dependent steps require verified predecessor credit. Refresh remaining targets after partial fills instead of repeating full size. Apply reviewed network settlement rules, including canonical sequencer inclusion for registered rollups.

## 4. Fix failures and continue

A product or test-harness defect is work to fix, not a human handoff. Capture the CLI failure and tell the user what failed, then inspect relevant source and development logs/state. Add a meaningful isolated regression, make the smallest correct fix, test, rebuild and resume. Preserve settled steps and their evidence. Re-run invalidated assertions and the affected workflow. If another attempt is necessary, reconcile prior outcomes, refresh the actual starting state and charge earlier costs against the same test accounting. Restore only when useful or when a particular test assertion needs that starting state; full baseline restoration is not a general retry gate.

After lost responses, cancellation, restart or uncertainty, reconcile the original submission with `operations` and `status`. Never create a new ID, send directly to a venue/RPC, clear reservations, reset state or repeat a financial action to escape uncertainty. After verified failure/reversion, a deliberate new attempt can use a new ID and fresh required authority, accounting for spent costs. Same-scope development authority can be renewed through GoFin when needed; expiry itself must never automatically replay a write.

Continue until the live-write scenario's financial effects and settlement are verified. Do not weaken assertions, skip failed steps, switch authorization mode or relabel synthetic evidence as live. Don't repeat the same funded failure without a changed, tested hypothesis. Account for retained funds/exposure and any chosen restoration reserve.

Stop new risk-increasing actions only for concrete constraints: missing supplied credentials/access/funds, unavailable external route/service, insufficient budget, unresolved external evidence, user stop, or a required scope expansion. Perform available authorized reconciliation and any useful optional cleanup, retain records and report the exact prerequisite. A default test limit that can be validly adjusted, or difficult optional restoration, is not by itself a blocker. Continue independent fixes while awaiting input. Long protocol delays are pending work: record original identities and the next eligible status check, never resubmit the source.

If diagnosis needs a direct read-only exchange API/RPC call, record why GoFin's public interface couldn't supply it and flag that discovery/feature gap. This fallback cannot establish that the public E2E flow passed. All financial writes, including cleanup, go through GoFin.

## 5. Verify final state and report

Verify the actual final balances, allocations, positions/debt, orders, collateral, permissions and costs against the scenario's expected effects. Restoration is optional: perform it when practical and useful, but skip or stop it when hard, impossible or disproportionate. Report retained assets/exposure, allowances, costs/dust, the restoration decision and any useful next action. A changed financial baseline or omitted optional restoration does not prevent a pass. Unresolved submissions or unverified required financial effects still prevent claiming the affected live-write scenario passed; report optional restoration attempts and any uncertainty separately. Cancel unused test grants/plans where supported. Stop only the selected broker when finished; preserve credentials, journal and private evidence. Stopping a broker does not cancel venue orders or transactions.

Report **passed**, **failed**, **blocked**, or **not run** per scenario, separating synthetic/fork/live-read/live-write evidence. State **automatic development approval** explicitly. Give verified live-write assertions, final financial state, restoration status (performed, partial or skipped), actual costs, budget overrides, fixes, tests and a private evidence link. Disclose any unresolved optional restoration attempt prominently, separately from the required scenario outcome. Never commit secrets, private account mappings, signed requests or raw live logs.

Human installation, credential isolation and real Touch ID remain **not run** unless observed. When relevant, hand off only that concrete human checklist after completing independent engineering and live verification. Do not defer ordinary adapter, plan or settlement debugging to the human.

Only when the human explicitly requests protected-runtime live verification, act as a user of GoFin. Derive commands, inputs, permissions and recovery steps from the public CLI's help, discovery, explanations, schemas and results. Do not read source code, inspect internal configuration or journal files, or call venue APIs/RPC directly to complete the normal user flow. Record missing discovery or unclear guidance as verification findings; do not silently fill gaps with implementation knowledge. If a blocker or bug appears, capture the CLI failure and tell the human before switching to developer diagnosis, then inspect only the relevant implementation. Credential protection, financial authorization and uncertain-submission recovery rules remain in force during diagnosis.
