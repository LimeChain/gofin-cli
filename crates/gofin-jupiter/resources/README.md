The pinned Jupiter IDL is the source of truth for both legacy and V2 route envelopes and every route enum payload; the bounded Borsh reader validates nested options, enums, booleans, vectors, and exact instruction termination. Jupiter's [v7.0.5 release notes](https://github.com/jup-ag/metis-binary/releases/tag/v7.0.5) document that the positive-slippage fee account follows the platform fee account; nonzero positive-slippage routing is rejected until GoFin has an approved intent field for that extra fee. RFQ `fill` fields are pinned from Order Engine V1. Trigger V1 instruction/account layouts are pinned from the published Limit Order V2 SDK source; the adapter independently checks the deployed program address and exact lifecycle effects. Synthetic byte fixtures are tested independently against these pinned layouts. Any source update requires a reviewed hash and fixture update.

The Order Engine IDL describes the 32-byte on-chain `fill` data (discriminator plus three arguments). Jupiter's current [Quoting and fills documentation](https://developers.jup.ag/docs/swap/routing/rfq/v1/quoting) specifies an additional 5-byte off-chain trailer: `fee_bps` (u16 LE), flags (exact-in/out and integrator-fee side), and `integrator_fee_bps` (u16 LE). The adapter parses the full 37-byte form and binds fee bps to the returned order; it accepts the 32-byte IDL-only legacy form only when no fee was quoted, requires exact-input mode, rejects nonzero unapproved integrator fees/reserved flag bits, and binds the fee mint to the input or output mint.

The Perps IDL is pinned at layout version `published-mainnet-beta-2026-10-11` (58 instructions). Perps decoder tests cover the current request instructions and the full current `IncreasePositionEvent` / `DecreasePositionEvent` suffixes, including exact collateral and price fields. Updating it requires a hash and fixture review.

The currently exposed Perps market-mint allowlist (SOL, ETH, BTC) follows the official [Perps API market-stats/pool-info schema](https://perps-api.jup.ag/v1/docs), which enumerates wrapped SOL `So11111111111111111111111111111111111111112`, wrapped ETH `7vfCXTUXx5WJV5JADk17DUJ4ksgau7utNKj4b963voxs`, and wrapped BTC `3NZ9JMVBmGAqocybic2c7LQCJScmgsAZ6vQqTDzcqmJh`. These are identity allowlists only; each transaction still has to prove the matching on-chain market pool, custody, collateral custody, mint and PDA.
